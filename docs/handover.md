## 1. Що таке цей проєкт (контекст одним абзацом)

MetaNetwork EQI — кросчейн мета-реєстр з мета-нативним токеном EQI. Production-інваріант: `A_active = 250,000,000 EQI` (абсолютний, без винятків). Поточний MVP — proof-of-mechanism на тестовому токені `tEQUI` у чотирьох EVM-тестнетах, з MVP-інваріантом `A_ACTIVE = 100,000 tEQUI`. Мета MVP — довести в реальному часі, що MetaRegistry може утримувати єдиний канонічний стан токена над кількома host-мережами, не будучи блокчейном, бриджем чи wrapped-token системою.

**Ключова парадигма:** MetaRegistry не виконує і не дублює — він переалоковує і фіксує стан (append-only). Host-мережі — лише середовища мінтингу й локального існування токена, не canonical truth layer.

## 2. Архітектурні інваріанти (НЕЗМІННІ для MVP)

| Інваріант | Значення | Коментар |
|---|---|---|
| `TOKEN` | tEQUI | тестовий токен, без економічної цінності |
| `TOTAL_MINTED` | 400,000 tEQUI | 100,000 × 4 мережі |
| `A_ACTIVE` | 100,000 tEQUI | **абсолютний інваріант. Позитивне відхилення на 1 tEQUI = негайний STOP** |
| `TOTAL_FROZEN` | 300,000 tEQUI | |
| `DECIMALS` (специфікація) | 0 | **ВІДХИЛЕННЯ: контракт реально задеплоєний з decimals=18.** Рішення Andrii: залишаємо decimals=18, документуємо як прийняте і свідоме відхилення від канонічної специфікації. Не виправляти, не переdeploying контракт через це. |
| `MIN_UNIT` | 1 tEQUI | |
| Старт активних / заморожених на мережу | 25,000 / 75,000 | лише початковий стан, після операцій може змінюватись |

Формули (мають виконуватись після кожної завершеної операції):
```
per-network: wallet_active + IT_ACTIVE + IT_FROZEN + UNAVAILABLE = 100,000
TOTAL_MINTED = Σ network_total = 400,000
A_ACTIVE = Σ(wallet_active + IT_ACTIVE + UNAVAILABLE) = 100,000
TOTAL_FROZEN = Σ(IT_FROZEN) = 300,000
```

**Тимчасове від'ємне відхилення A_ACTIVE дозволене** лише в transitional-стані між source freeze і target unfreeze. **Позитивне відхилення — заборонене категорично, незалежно від причини.**

## 3. Дві площини свободи (Dual Freedom Planes)

- **Plane 1 — THROUGH_METAREGISTRY**: MetaRegistry повністю контролює і виконує операцію (OperationEnvelope, SourceOperation, TargetSettlement, EventRecord).
- **Plane 2 — DIRECT_HOST_NETWORK**: користувач рухає токен напряму в host-мережі. MetaRegistry не виконує, але зобов'язаний спостерігати й фіксувати стан.
  - **DIRECT_HOST_NETWORK_VIA_DAPP** — нормальний шлях: EQI DApp перевіряє адресу одержувача (address policy) ДО підпису MetaMask. Невідома адреса → reject ДО підпису.
  - **DIRECT_HOST_NETWORK_OUTSIDE_DAPP_OBSERVED** — виключний шлях: користувач рухає токен поза DApp (голий MetaMask). Якщо ціль — невідома реєстру адреса → токен стає `UNAVAILABLE`, але лишається всередині `A_ACTIVE` (не зникає, не STOP, просто недоступний для нормальних MVP-операцій).

Важливо: **outside execution path ≠ outside accounting/visibility scope.** MetaRegistry завжди має знати, де токен, навіть якщо не контролював рух.

## 4. Рольова межа (хто що робить)

```
User → MetaMask (wallet provider only)
     → EQI DApp (ОБОВ'ЯЗКОВИЙ user-facing intent/execution layer — голий MetaMask НЕ є нормальним MVP-flow)
     → MetaRegistry (canonical state accounting/visibility layer)
     → TML (controlled execution layer)
     → Host blockchain (локальне середовище виконання)
     → Observer/Watcher → MetaRegistry accounting
```

DApp НЕ має бути джерелом бізнес-логіки — вона викликає вже перевірену backend state-логіку. Executor НЕ приймає рішень — лише виконує вже валідовані команди.

## 5. Газова модель (канонічна, УТОЧНЕНО 2026-06-17 — див. розділ 12)

- Вхід у MetaNetwork: реальна on-chain транзакція (тестувальник → відповідний IT-EOA). Газ платить відправник (тестувальник) у своїй мережі.
- **Внутрішній перерозподіл** (записи freeze/unfreeze, зміна wallet_active/IT_ACTIVE/IT_FROZEN у канонічному стані MetaRegistry, узгодження source↔target): **0 газу** — це лише запис у backend, не on-chain дія.
- Вихід з MetaNetwork (видача тестувальнику — будь-то Treasury Distribution або фінальний крок Cross-Network Transfer): реальна on-chain транзакція (відповідний IT-EOA → гаманець тестувальника). Газ платить **сам IT-EOA** зі свого балансу рідної монети мережі (ETH/BNB/POL/ETH); саме тому критично важливий моніторинг газу IT-гаманців (розділ 7, п.2).
- IT-гаманці = одночасно й фізичне сховище мінтингу, і виконавець реальних on-chain переказів на вхід/вихід. **Лише середній крок (бухгалтерський перерозподіл між freeze і unfreeze) є записом без газу — самі вхід і вихід завжди реальні on-chain транзакції.**

## 7. Backend-вимоги (зафіксовані рішення 2026-06-16)

1. **`ethers.js getFeeData()` — обов'язково** для автоматичного gas price. Фіксований gas price НЕ використовувати.
2. **Моніторинг газу IT-гаманців**: threshold для Sepolia/BNB/Arbitrum < 0.005 ETH/BNB, для Amoy < 0.01 POL → WARNING у логах + endpoint `GET /health/gas`.
3. `POST /treasury/distribute` та фінальний крок `POST /transfer` (target unfreeze → видача отримувачу) **ВИКОНУЮТЬ реальну on-chain транзакцію** з відповідного IT-EOA на гаманець тестувальника (УТОЧНЕНО 2026-06-17, див. розділ 12 — це скасовує попереднє формулювання "лише запис, не on-chain"). Внутрішній крок (freeze-запис, перерозподіл між мережами) лишається чистим записом без газу.
4. On-chain транзакції відбуваються при вході користувача в MetaNetwork (тестувальник → IT-EOA, газ платить тестувальник) і при виході з MetaNetwork (IT-EOA → тестувальник, газ платить IT-EOA зі свого балансу). Внутрішній перерозподіл між freeze і unfreeze — без газу, лише запис.
5. IT-гаманці невидимі в публічних записах (див. 6.1).
6. DApp показує баланс tEQUI напряму через ethers.js RPC, **не через MetaMask UI**.
7. Роздача tEQUI тестувальникам — ручний процес: тестувальник надсилає адресу адміну → адмін роздає через `POST /treasury/distribute`.

### Очікувані REST endpoints (з архітектурних документів, MVP backend):
```
POST /genesis
POST /treasury/distribute
POST /transfer
GET  /state
GET  /transparency
GET  /events
GET  /health/gas
```
Claude Code має перевірити, які з них вже реалізовані в `backend/`, а яких ще немає.

Мета: **Treasury Distribution to Testers** — роздати активну частину з `IT_ACTIVE` у closed tester wallet set. **Це реальна on-chain транзакція з IT-EOA на гаманець тестувальника** (див. розділ 12 — уточнення 2026-06-17, скасовує попередню формулу "лише запис").

Орієнтовний план (з документу Next Implementation Sequence v0.1, розділ 9, адаптовано з урахуванням розділу 12):

1. Клонувати/синхронізувати репо локально (вже маєш доступ).
2. Перевірити фактичний стан `backend/` — чи встановлено `ethers`, чи є `.env` з IT-ключами та RPC endpoints.
3. Якщо `.env` відсутній — створити (з IT-ключами і RPC endpoints; ключі НЕ комітити в публічний репо).
4. Підключити backend до реальних тестнетів через ethers.js.
5. Реалізувати/перевірити Treasury Distribution: перевірка інваріантів → **реальна on-chain ERC-20 transfer з IT-EOA на адресу тестувальника** → дочекатись підтвердження → лише тоді записати `TREASURY_DISTRIBUTION_APPLIED` зі статусом COMPLETED і tx_hash (детальніше — розділ 12).
6. Реалізувати/перевірити `GET /health/gas` з моніторингом балансу IT-гаманців (пороги — розділ 7, п.2) — критично важливо, бо без газу на IT-EOA реальна видача (п.5) не відбудеться.
7. Перед роздачею — **отримати від Andrii фінальний список tester-адрес**, якщо він ще не зафіксований у репо.
8. Після кожної роздачі — перевірити інваріанти (розділ 2) і append-only EventRecord з tx_hash як доказом.

**Stage Gate перед переходом до Step 8 (Executor):** Executor можна починати лише якщо OperationEnvelope, EventRecord, InvariantSnapshot і TransparencySnapshot стабільні для testnet-інтеграції, і Treasury Distribution коректно відображена в канонічному стані без invariant mismatch.

## 9. Заборонено в цій сесії (Stage Gate guardrails)

- Не починати Executor/Watcher/DApp-роботу, поки Treasury Distribution (Step 7) не підтверджена як стабільна.
- Не дозволяти `A_ACTIVE` перевищити 100,000 tEQUI навіть тимчасово в "завершеному" стані.
- Не трактувати on-chain баланс як джерело правди понад MetaRegistry — будь-яка розбіжність → `RECONCILIATION_REQUIRED`, не мовчазне перезаписування.
- Не редеплоїти контракт через decimals=18 — це прийняте відхилення (розділ 2).
- Не публікувати IT-адреси чи приватні ключі в публічних записах/коміти.

## 12. УТОЧНЕННЯ 2026-06-17 — реальна модель on-chain/off-chain операцій (ПРІОРИТЕТНЕ над розділами 5 і 8)

**Це найновіше рішення Andrii, отримане після початкового handover, в окремому уточнюючому обговоренні. Розділи 5 і 8 вище вже виправлені відповідно до цього розділу — даний розділ є детальним поясненням і обґрунтуванням, чому саме так.**

Причина уточнення: попереднє формулювання "Treasury Distribution і Transfer — лише запис у MetaRegistry, не on-chain транзакція" було architecturally неточним. Якщо токен не рухається on-chain реально, тестувальник ніколи не побачить tEQUI у своєму MetaMask — а це підриває саму мету MVP (довести роботу в реальному часі на реальних testnets).

### Підтверджена модель на прикладі: Тестер1 (мережа A) надсилає 100 tEQUI Тестеру2 (мережа B)

Це **три окремі реальні кроки**, не один:

1. **Вхід у MetaNetwork (реальна on-chain транзакція).** Тестер1 підписує в MetaMask і відправляє 100 tEQUI зі свого гаманця на IT-A (скарбничка мережі A). **Тестер1 сам платить газ мережі A.** У термінах стейт-машини це відповідає source freeze: wallet_active[A] -100, IT_FROZEN[A] +100 — але тепер це супроводжується справжнім ERC-20 transfer, а не лише записом.

2. **Внутрішній перерозподіл у MetaRegistry (0 газу, лише запис).** Backend фіксує перехід стану: узгоджує source freeze в мережі A з target unfreeze в мережі B, рахує A_ACTIVE/TOTAL_FROZEN, пише EventRecord і InvariantSnapshot. Жодної on-chain дії на цьому кроці немає.

3. **Вихід з MetaNetwork (реальна on-chain транзакція).** IT-B (скарбничка мережі B) виконує реальний ERC-20 transfer 100 tEQUI на гаманець Тестера2. **Газ цієї транзакції платить сам IT-B-EOA** зі свого балансу рідної монети мережі B (тобто backend підписує транзакцію сервісним ключем IT-B через GCP KMS і відправляє її, оплачуючи gas fee з балансу IT-B). Це і є причина, чому моніторинг газу IT-гаманців (розділ 7, п.2 і `GET /health/gas`) критично важливий — якщо на IT-B немає газу, крок 3 не виконається і операція "застрягне" між source freeze і target unfreeze.

### Те саме застосовується до Treasury Distribution (Step 7)

Підтверджено Andrii: Treasury Distribution (видача tEQUI тестувальнику з IT_ACTIVE вперше, без "відправника"-тестувальника) **за тим самим принципом** має виконувати реальну on-chain транзакцію з відповідного IT-EOA на гаманець тестувальника, з газом, який платить сам IT-EOA. Це аналог кроку 3 вище, просто без кроку 1 (бо немає вхідного переказу — це перша видача).

### Що це означає для коду (Step 7 і Step 8)

- `POST /treasury/distribute` має: (а) перевірити інваріанти й баланс IT_ACTIVE у MetaRegistry, (б) **виконати реальну on-chain ERC-20 transfer** з відповідного IT-EOA на адресу тестувальника через ethers.js (з `getFeeData()`, як зафіксовано в розділі 7 п.1), (в) дочекатись підтвердження транзакції, (г) лише після цього записати в MetaRegistry `TREASURY_DISTRIBUTION_APPLIED` зі статусом COMPLETED і tx_hash як доказ.
- `POST /transfer` (cross-network) має реалізувати всі три кроки вище: прийняти доказ вхідної транзакції від тестувальника (або самостійно її верифікувати через observer/watcher), зробити внутрішній freeze/unfreeze запис, і **виконати реальну вихідну on-chain транзакцію** з IT-EOA цільової мережі.
- Якщо вихідна on-chain транзакція (крок 3) не пройшла (немає газу, RPC недоступний тощо) — операція має лишатись у статусі `TARGET_UNFREEZE_PENDING` чи подібному, **не** `COMPLETED`. Не позначати операцію завершеною, доки on-chain транзакція виходу не підтверджена.
- Backend має зберігати tx_hash для обох on-chain кроків (вхід і вихід) як частину EventRecord — це і є evidence для traceability.

**Якщо в коді backend вже реалізовано `/treasury/distribute` чи `/transfer` за старою (чисто обліковою) логікою — це потребує доопрацювання, а не вважається завершеним кроком. Повідом Andrii, якщо знайдеш таку розбіжність, перед тим як продовжувати.**
