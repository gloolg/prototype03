# MetaRegistry State — пояснення полів у DApp (блок 6)

Довідник для `backend/public/index.html`, блок 6 "MetaRegistry State", функція
`loadState()` (рядки 912–930 станом на 2026-07-02). Викликає `GET /state` →
`stateManager.getFullState()` (`backend/src/stateManager.js:458-471`), який
повертає прямий знімок серверного in-memory об'єкта `_state` — **не** живий
запит до блокчейну (див. розділ "Важливо" наприкінці).

Кожна мережа (`state.networks[net_id]`) — це об'єкт, створений
`createNetworkState()` (`simulator/src/stateFactory.js:50-74`) з полями:
`wallet_active_total, IT_ACTIVE, IT_FROZEN, UNAVAILABLE` і геттером
`network_total`, що завжди повинен дорівнювати 100 000
(`MINTED_PER_NETWORK`).

---

## IT_ACTIVE

**Що це:** "вільна" частина скарбнички (IT-EOA) мережі — та, яку можна
роздати тестувальникам через `/treasury/distribute`. Аналог "готівки в касі,
доступної для видачі".

**Де формується:**
- Початкове значення при genesis — `simulator/src/genesis.js:105`, з
  `calculateActiveShares()` (`networkAllocation.js`), типово 25 000/мережу
  для N=4.
- Дзеркалиться в `TreasuryState.IT_ACTIVE` (`genesis.js:116`) — обидва поля
  мають завжди збігатись (перевіряється в `invariants.js:262-269`).

**Що збільшує:**
- `stateManager.js:734` — `loadOnChainBalances()`, викликається **один раз
  при кожному старті сервера**. Перезаписує `IT_ACTIVE` реальним ончейн-
  балансом IT-EOA мінус поточний `IT_FROZEN`: `it_active = max(0, itOnChain
  - it_frozen)`. Це єдиний механізм, що синхронізує це поле з блокчейном.
- `networkRebalance.js:65` — при додаванні нової мережі (`rebalanceOnNetworkAdd`,
  `/admin/network-add`) нова мережа отримує свою частку.

**Що зменшує:**
- `simulator/src/treasury.js:147` — `applyTreasuryDistribution()`
  (`POST /treasury/distribute`): `IT_ACTIVE -= amount`, `wallet_active += amount`
  на тому ж гаманці. Це основний, штатний спосіб зміни поля.
- `networkRebalance.js:44` — коли додається нова мережа, **існуючі** мережі
  віддають частину `IT_ACTIVE` в `IT_FROZEN` (структурне перерозприділення,
  не реальний рух коштів — просто перепідрахунок часток).
- `stateManager.js:781` — `applyCabinetWithdraw()`: списання при виведенні
  коштів із Cabinet (`/cabinet/withdraw`).

**НЕ зачіпається:** крос-мережевими freeze/unfreeze операціями
(`crossNetwork.js`) — ті працюють виключно з парою `wallet_active ↔
IT_FROZEN`, `IT_ACTIVE` там не бере участі.

**Що означає для користувача DApp:** практично нічого напряму. Це
операційний показник "скільки скарбничка мережі ще може роздати
тестувальникам", корисний лише адміну, що виконує roздачі. Звичайний
користувач ніколи не взаємодіє з цим числом безпосередньо.

## IT_FROZEN

**Що це:** структурний резерв IT-EOA, що **тимчасово блокується** як
забезпечення під крос-мережеву маршрутизацію. Не доступний для прямої
роздачі — тільки для проведення переказів між мережами.

**Де формується:**
- Genesis — `genesis.js:106`, з `calculateFrozenReserve()` = minted_per_network
  − IT_ACTIVE (типово 75 000/мережу для N=4).

**Що збільшує:**
- `crossNetwork.js:259` — `applySourceFreeze()`: коли **джерельна** мережа
  крос-мережевого переказу "заморожує" суму — `wallet_active -= amount`,
  `IT_FROZEN += amount`. Викликається для кожного джерела в
  `/transfer`, `/entry`, MSE-потоці.
- `networkRebalance.js:46` — існуючі мережі при додаванні нової отримують
  приріст `IT_FROZEN` за рахунок зменшення `IT_ACTIVE` (перерозподіл, не
  реальний рух коштів).

**Що зменшує:**
- `crossNetwork.js:351` — `applyTargetUnfreeze()`: коли **цільова** мережа
  переказу видає суму отримувачу — `IT_FROZEN -= amount`, `wallet_active +=
  amount` на гаманці отримувача. Це завершальний крок будь-якого
  крос-мережевого переказу.

**НЕ зачіпається:** `/treasury/distribute` (працює лише з `IT_ACTIVE`).

**Що означає для користувача DApp:** так само як `IT_ACTIVE` — суто
операційний/бухгалтерський показник стану скарбнички. У звичайному потоці
DApp (Type A cross-network transfer) значення `IT_FROZEN` цільової мережі
тимчасово змінюється **під час** вашого переказу, але сам користувач цього
не бачить і не повинен бачити — він бачить лише "переказ виконано/не
виконано".

## wallet_active_total

**Що це:** сума `wallet_active` **усіх** зареєстрованих гаманців на цій
мережі — не баланс якогось одного гаманця, а агрегат по всій мережі.

**Де рахується:**
- Genesis — стартує з 0 (`genesis.js:104`, коментар "no wallets funded yet").
- Підтримується **інкрементально**: кожна операція, що змінює конкретний
  `wallet.wallet_active`, **одночасно** змінює `net.wallet_active_total` на
  ту саму дельту в тій самій функції (не перераховується "з нуля" при
  кожному читанні):
  - `treasury.js:150` (+ при роздачі),
  - `crossNetwork.js:258/354` (− при заморозці джерела / + при розморозці
    цілі),
  - `observation.js:121/133` (Observer: − у відправника / + у відомого
    отримувача при прямому ончейн-переказі гаманець↔гаманець),
  - `stateManager.js:802` (+ при `applyCabinetWithdraw`).
- **Дійсно перераховується з нуля** (сума реальних значень) лише у двох
  місцях:
  - `stateManager.js:109` (`_walletActiveTotalFromDB`) — при відновленні
    стану після рестарту сервера, `SUM(active_balance) FROM wallet_balance`.
  - `stateManager.js:710-727` (`loadOnChainBalances()`) — при кожному
    старті сервера, як сума **реальних** ончейн-балансів усіх відомих
    гаманців мережі.

**Чому показується сума, а не окремі гаманці:** `state.wallets` — це плаский
словник, ключ `"мережа:адреса"`, без групування. Секція "MetaRegistry State"
у DApp — це високорівневий підсумок **по мережі**, не провідник по
гаманцях. Список окремих гаманців з балансами існує окремо —
`GET /admin/wallets` (Bearer-auth, лише адмін).

**Що означає для користувача DApp:** нічого особисто корисного — це
агрегат **чужих** балансів разом із власним. Власний баланс користувач
бачить окремо, у картці "tEQUI Balance" (живий `balanceOf()` через RPC, не
з цього блоку).

## UNAVAILABLE

**Що це:** сума токенів, які Observer побачив на ланцюгу як переказані на
**незареєстровану** в MetaRegistry адресу — тобто реєстр *знає*, що вони
існують і кудись пішли, але **не може** їх більше відстежувати/маршрутизувати.

**Коли з'являється:** виключно в `simulator/src/observation.js:185`,
усередині `reconcileObservedTransfer()`, гілка "Case 2:
UNKNOWN_REGISTRY_ADDRESS" — коли Observer фіксує прямий ончейн-переказ
гаманець→гаманець, і **отримувач не є відомим тестовим/зареєстрованим
гаманцем**:
```
state.networks[network_id].UNAVAILABLE += amount;
```
(джерело — реальний відправник — одночасно втрачає цю суму з
`wallet_active_total`, тож загальна сума мережі не змінюється).

**Важливо:** у поточному коді **немає жодного шляху зменшити** це поле —
воно тільки зростає. Це односторонній "бакет втраченого з-під контролю", не
"заморожене до повернення".

**Значення для інваріанту:** `UNAVAILABLE` **входить** до `A_ACTIVE`
(`invariants.js:33`: `a_active_current = wallet_active_total + IT_ACTIVE_total
+ UNAVAILABLE_total`). Тобто токени, що пішли на невідому адресу, і далі
рахуються як "активні" для цілей інваріанту 100 000 — вони фізично існують,
просто поза видимістю/контролем реєстру. Це навмисне архітектурне рішення:
`A_ACTIVE` ніколи не повинен зростати понад 100 000, а `UNAVAILABLE` — це
спосіб чесно визнати "ми не знаємо, де це", не порушуючи інваріант і не
вигадуючи фіктивне "спалювання" токенів.

**Що означає для користувача DApp:** сигнал про проблему **системного**
рівня (хтось відправив токени повз DApp на незнайому адресу), не пов'язаний
з конкретними діями користувача, що дивиться на екран. Чисто діагностичне
поле для адміна.

## event_count

**Що це:** `state.events.length` (`stateManager.js:468`) — загальна
кількість усіх append-only записів `EventRecord`, коли-небудь створених
**у всій системі** (не по мережі — глобально), з моменту genesis.

**З чого складається:** буквально кожна дія, що змінює стан, дописує один
або кілька записів (наприклад, один крос-мережевий переказ породжує
`ENVELOPE_CREATED`, `PRE_VALIDATION_OK`, `SOURCE_FREEZE_APPLIED` (на кожне
джерело), `TEMP_ACTIVE_DELTA_RECORDED`, `TARGET_UNFREEZE_APPLIED`,
`INVARIANT_SNAPSHOT` (кілька разів), `OPERATION_COMPLETED` — тобто одна
операція користувача = 5-10+ записів у журналі).

**Обмеження:** немає жодного ліміту чи очищення — append-only за дизайном
(`db.js`, коментар "Rows are NEVER updated or deleted after insert"). Число
монотонно зростає весь час роботи системи; єдиний спосіб скинути — повне
видалення БД і новий genesis.

**Що означає для користувача DApp:** нічого практичного — це розмір
внутрішнього журналу аудиту, корисний тільки для розуміння "скільки історії
накопичилось", типове debug/ops-поле.

## status

**Можливі значення** (`simulator/src/constants.js`, `SYSTEM_STATUS`):

| Значення | Коли встановлюється | Наслідок |
|---|---|---|
| `UNINITIALIZED` | Початкове, до `/genesis` (`stateFactory.js:24`) | Майже всі операції відхиляються (`GENESIS_NOT_COMPLETED`) |
| `ACTIVE` | Один раз, наприкінці `initializeGenesis()` (`genesis.js:147`) | Штатний робочий стан |
| `STOP` | `triggerStop()` (`invariants.js:314-316`) — викликається при **будь-якому** порушенні критичного інваріанту: позитивна дельта `A_ACTIVE`, провал traceability-перевірки, провал `checkInvariants()` після операції. Точки виклику: `treasury.js:177/187`, `crossNetwork.js:303/397/528`, `observation.js:174/243` | **Уся** система зупиняється — `assertActive()` відхиляє геть усі подальші операції з причиною `SYSTEM_STOP`, для будь-якого гаманця й мережі |

**Важливий нюанс:** у поточному коді **немає жодного шляху вийти зі стану
`STOP`** — ані ендпоінта, ані функції "resume"/"clear". Якщо система
зупинилась, це постійно, доки не буде ручне втручання в БД або новий
genesis (що вимагає видалення БД).

**Що означає для користувача DApp:** це **єдине** поле з блоку 6, яке
теоретично зачіпає кінцевого користувача напряму — якщо `status !== ACTIVE`,
жодні перекази не працюватимуть, і користувач це відчує через провал
операцій. Але сире значення `"STOP"` без причини незрозуміле для
непідготовленої людини — краще подавати як прозорий індикатор (як уже
зроблено в `transparency.html`, бейдж ACTIVE/STOPPED/VIOLATION з
поясненням), а не сирий рядок у технічній таблиці.

## Підсумок: чи потрібен цей блок кінцевому користувачу DApp?

| Поле | Користувачу DApp | Адміну/дебагу |
|---|---|---|
| `IT_ACTIVE` | ✗ не потрібне | ✓ операційний стан скарбнички |
| `IT_FROZEN` | ✗ не потрібне | ✓ стан крос-мережевого резерву |
| `wallet_active_total` | ✗ агрегат чужих балансів | ✓ здоров'я пулу мережі |
| `UNAVAILABLE` | ✗ не пов'язане з діями користувача | ✓ сигнал "токени пішли повз реєстр" |
| `event_count` | ✗ розмір журналу, не інформативний | ✓ розмір історії |
| `status` | ~ впливає на нього, але сире значення незрозуміле | ✓ критичний health-індикатор |

**Висновок підтверджує вже прийняте рішення прибрати блоки 6
("MetaRegistry State") і 7 ("Recent Events") з `index.html` після
завершення тестування.** Жодне з полів не несе цінності для звичайного
користувача DApp у представленому вигляді — це суто ops/debug-панель, що
концептуально належить `admin.html`, а не user-facing DApp. Єдиний
частково корисний сигнал (`status !== ACTIVE`) варто, якщо взагалі
залишати, показувати як компактний індикатор здоров'я системи (на кшталт
бейджа в `transparency.html`), а не як рядок у сирій діагностичній таблиці.

## Важливо: це не "живі" дані з блокчейну

Усі числа в цьому блоці — знімок **внутрішньої бухгалтерії реєстру**
(`_state` в пам'яті сервера, дзеркало в SQLite), яка оновлюється **лише**
реакцією на конкретні операції (перелічені вище) плюс одноразову
синхронізацію з блокчейном при кожному старті сервера
(`loadOnChainBalances()`, `stateManager.js:701-760`). Якщо рух токенів
стається **повз** реєстр (наприклад, прямий переказ гаманець→IT-EOA не
через кнопку DApp, без наступного виклику `/entry`), ці числа тимчасово
розходяться з реальністю на блокчейні — аж до наступного рестарту сервера
або явної операції реєстру. Живі дані для конкретної адреси —
`GET /registry/balances?address=`; повна звірка реєстру з блокчейном по
всіх мережах — `GET /admin/onchain-invariant` (Bearer-auth).
